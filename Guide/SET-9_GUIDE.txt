Q1. Jenkins Pipeline for a Java Project [25 Marks]
--------------------------------------------------------------------------------

OVERVIEW:
Automate the build of Maven Java project (https://github.com/savram674/MJP.git) using a Jenkins Declarative Pipeline, display the Pipeline View, and list 5 microservices plugins.

STEP 1: Open Jenkins Web Interface
  Open browser: `http://localhost:8080` (or Jenkins server IP).

STEP 2: Create a New Pipeline Project
1. Click **New Item** on the left menu.
2. Enter Item Name: `JavaMavenPipeline`
3. Select **Pipeline** (not Freestyle) and click **OK**.

STEP 3: Configure Pipeline Script
1. Scroll down to the **Pipeline** section.
2. Select Definition: **Pipeline script**.
3. In the script editor box, paste the following declarative pipeline:

pipeline {
    agent any

    tools {
        maven 'Maven'  // Name of Maven tool configured in Manage Jenkins -> Tools
    }

    stages {
        stage('Checkout Code') {
            steps {
                echo 'Pulling code from GitHub repository...'
                git branch: 'master', url: 'https://github.com/savram674/MJP.git'
            }
        }

        stage('Compile') {
            steps {
                echo 'Compiling Java Source files...'
                sh 'mvn compile'  // Use 'bat "mvn compile"' if running Jenkins on Windows
            }
        }

        stage('Run Unit Tests') {
            steps {
                echo 'Executing JUnit test cases...'
                sh 'mvn test'     // Use 'bat "mvn test"' on Windows
            }
        }

        stage('Package Application') {
            steps {
                echo 'Packaging application into JAR...'
                sh 'mvn clean package'  // Use 'bat "mvn clean package"' on Windows
            }
        }
    }

    post {
        success {
            echo 'Pipeline Executed Successfully! Artifacts generated in target directory.'
        }
        failure {
            echo 'Pipeline Failed! Check console log for compilation or test failures.'
        }
    }
}

4. Click **Save**.

STEP 4: Run the Pipeline Build
1. Click **Build Now** on the left menu.
2. Under "Build History", click on build `#1`.
3. Check the "Stage View" on the project main page showing all green blocks.
4. Click **Console Output** to verify the logs.

STEP 5: Setup Pipeline View (Jenkins UI)
1. Click the `+` (New View) icon on the Jenkins main dashboard tab bar.
2. Enter View Name: `MJP-Pipeline-View`
3. Select **Build Pipeline View** (or **Pipeline Stage View** / **Dashboard View**).
4. Click **Create**, choose initial job `JavaMavenPipeline`, and click **OK**.

FIVE IMPORTANT JENKINS PLUGINS FOR MICROSERVICES CI/CD:
1. **Git Plugin**: Integrates Git version control, automatically triggering builds on commits, pull requests, and polling branches.
2. **Pipeline Maven Integration Plugin**: Automatically records Maven builds, test results, and dependencies, optimizing artifact caching across microservice pipelines.
3. **Docker Pipeline Plugin**: Enables building Docker container images, running containers as build agents, and pushing microservice images to container registries (Docker Hub/ECR).
4. **Kubernetes Continuous Deploy (or Kubernetes CLI Plugin)**: Automates rolling updates and zero-downtime deployment of microservice container pods to Kubernetes clusters.
5. **SonarQube Scanner Plugin**: Performs automated static code analysis, code coverage, vulnerability detection, and enforces quality gates for each microservice before deployment.

WHAT TO SHOW TO MAM:
1. Jenkins **Stage View / Pipeline View** showing all stages (Checkout Code -> Compile -> Run Unit Tests -> Package Application) marked with green boxes.
2. **Console Output**: Scroll to bottom showing:
   `[INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0`
   `[INFO] BUILD SUCCESS`
   `Finished: SUCCESS`
3. The 5 Jenkins plugins with their microservice purposes explained.

Q2. Working with Minikube (Nginx Service Deployment) [25 Marks]
--------------------------------------------------------------------------------

OVERVIEW:
Deploy Nginx on Minikube, expose on port 8090, scale to 4 replicas, verify in browser and CLI, demonstrate pod and deployment deletion, and troubleshoot health check failures.

STEP 1: Start Minikube
Execute in terminal:
  minikube start --driver=docker

STEP 2: Create Nginx Deployment
Execute in terminal:
  kubectl create deployment nginx-service-deploy --image=nginx

STEP 3: Expose Service on Port 8090
Execute in terminal:
  kubectl expose deployment nginx-service-deploy --type=NodePort --port=8090 --target-port=80 --name=nginx-8090-svc

STEP 4: Scale the Deployment to 4 Replicas
Execute in terminal:
  kubectl scale deployment nginx-service-deploy --replicas=4

STEP 5: Verify Deployment, Nodes, Pods, and Services
Execute in terminal:
  kubectl get deployments
  kubectl get nodes
  kubectl get pods -o wide
  kubectl get svc nginx-8090-svc

STEP 6: Verify in Browser on localhost:8090
Execute in terminal:
  # Forward port 8090 to local port 8090:
  kubectl port-forward svc/nginx-8090-svc 8090:8090
  # Now open your browser and visit:
  # http://localhost:8090

STEP 7: Demonstrate Deleting a Pod (Self-Healing Demo)
Execute in terminal:
  # Copy one pod name from kubectl get pods:
  kubectl delete pod <pod-name-from-step-5>
  # Immediately run:
  kubectl get pods
  # Note: ReplicaSet immediately provisions a brand-new Pod in replacement!

STEP 8: Demonstrate Deleting the Deployment
Execute in terminal:
  kubectl delete deployment nginx-service-deploy
  kubectl delete svc nginx-8090-svc
  kubectl get pods  # (Shows pods terminating)

WHAT TO SHOW TO MAM:
1. Terminal: Output of `kubectl get deployments` showing `nginx-service-deploy` with `READY 4/4`.
2. Terminal: Output of `kubectl get pods -o wide` showing 4 pods in `Running` state across nodes.
3. Terminal: Output of `kubectl get svc` showing `nginx-8090-svc` with port `8090`.
4. Browser: Open `http://localhost:8090` showing the "Welcome to nginx!" default landing page.
5. Deletion Demo: Delete 1 pod in front of examiner using `kubectl delete pod <name>` and run `kubectl get pods` to show self-healing (new pod spawned).

SCENARIO ANSWER (Q2.6 - Pods failing health checks):
- How to identify root cause:
  1. Run `kubectl describe pod <pod-name>`: Check the "Events" section at the bottom for `Unhealthy: Liveness/Readiness probe failed HTTP status 500/404` or `Connection refused`.
  2. Run `kubectl logs <pod-name>` or `kubectl logs <pod-name> --previous`: Inspect application logs to check if the app crashed, deadlocked, or encountered runtime exceptions.
  3. Verify probe settings: Check if probe endpoint path (`/healthz`), port, `initialDelaySeconds`, `timeoutSeconds`, or `periodSeconds` are set incorrectly before the app finishes initializing.
- How to fix it:
  1. Increase `initialDelaySeconds` in deployment YAML so slow-starting containers have enough time to boot.
  2. Correct port or health endpoint path in liveness/readiness probe definition.
  3. Resolve application exceptions or database connection failures detected in the pod logs.

Q3. Nagios – Host and Service Monitoring [25 Marks]
--------------------------------------------------------------------------------

OVERVIEW:
Set up Nagios using Docker, start web interface, demonstrate host & service monitoring status, and troubleshoot connection and host discovery issues.

STEP 1: Run Nagios Core in Docker
Execute in terminal:
  docker run -d --name nagios-monitor -p 8080:80 jasonrivers/nagios:latest

STEP 2: Verify Nagios Container is Running
Execute in terminal:
  docker ps -f name=nagios-monitor
  docker logs nagios-monitor

STEP 3: Access Nagios Web Interface
1. Open web browser: `http://localhost:8080` (or `http://<ec2-ip>:8080`)
2. Enter default login credentials:
   - Username: `nagiosadmin`
   - Password: `nagios`

STEP 4: Demonstrate Monitoring Status and Status Meanings
1. In the left navigation pane under **Current Status**:
   - Click **Hosts**:
     Shows `localhost` host status as **UP** (highlighted in Green).
   - Click **Services**:
     Shows critical service checks for localhost:
     * HTTP: OK (Green)
     * PING: OK (Green)
     * SSH: OK (Green)
     * Root Partition: OK (Green)
     * Current Load: OK (Green)
     * Total Processes: OK (Green)
2. Explanation of Status Indicators:
   - **UP / OK (Green)**: Host/Service is healthy and operating within threshold parameters.
   - **WARNING (Yellow)**: Service is operational but has crossed warning threshold (e.g. high CPU load or 80% disk full).
   - **CRITICAL (Red)**: Service has failed, crashed, or crossed critical limit (e.g. service unresponsive, 95% disk full).
   - **UNKNOWN (Orange)**: Nagios plugin cannot determine status (e.g. check plugin missing or timed out).
   - **PENDING (Grey)**: Service has recently been registered and has not undergone its first active check cycle.

WHAT TO SHOW TO MAM:
1. Browser: Nagios Web Dashboard at `http://localhost:8080/nagios/`.
2. Navigation: Click **Hosts** to display `localhost` marked **UP** in green.
3. Navigation: Click **Services** to show the table of services (HTTP, PING, SSH, Load, Disk) with Status **OK** in green.
4. Terminal: Show `docker ps` displaying `nagios-monitor` container running on port 8080.

SCENARIO-BASED ANSWERS FOR VIVA / LAB EVALUATION:
Q3.4: Web interface displays "Unable to connect to Nagios process":
  - Root Cause: The core Nagios daemon (`/usr/local/nagios/bin/nagios`) has stopped running or crashed, even though the Apache web server hosting the PHP/CGI interface is still up.
  - How to resolve:
    1. Check Nagios service status inside container:
       `docker exec -it nagios-monitor service nagios status`
    2. Start the Nagios service:
       `docker exec -it nagios-monitor service nagios start`
    3. Check for stale lock file `/usr/local/nagios/var/nagios.lock` and remove it if process died abruptly.
    4. Inspect `/usr/local/nagios/var/nagios.log` for segmentation faults or configuration load errors.
Q3.5: Added a new host in Nagios, but it is not appearing on the web interface:
  - How to check:
    1. Pre-flight verification: Run the Nagios configuration pre-flight check to test for syntax errors:
       `docker exec -it nagios-monitor /usr/local/nagios/bin/nagios -v /usr/local/nagios/etc/nagios.cfg`
    2. Confirm host config inclusion: Verify that `cfg_file` or `cfg_dir` directive in `/usr/local/nagios/etc/nagios.cfg` points to your newly created host file.
    3. Restart/reload daemon: Nagios does not automatically reload on file edits. You must reload or restart:
       `docker exec -it nagios-monitor service nagios reload` (or `restart`).
    4. Contact / Group permissions: Ensure the host definition assigns `contact_groups` that include `nagiosadmin`, otherwise the user cannot see it in the UI due to CGI authorization filters (`cgi.cfg`).

Q4. AWS EC2 – Launch and Deploy a Web Application [25 Marks]
--------------------------------------------------------------------------------

OVERVIEW:
Deploy Maven Web Application (https://github.com/savram674/BookBank.git) on an Ubuntu EC2 instance, build Docker image, start container, and access via EC2 Public IPv4.

STEP 1: Launch EC2 Instance & Configure Security Group
1. AWS Console -> EC2 -> Launch Instance.
2. Name: `BookBank-Server`
3. AMI: Ubuntu Server 22.04 LTS (HVM), SSD Volume Type.
4. Instance Type: t2.micro (Free Tier eligible).
5. Key Pair: Select existing key or create new `.pem` key.
6. Network / Security Group Rules:
   - Allow SSH: Port 22 | Source: 0.0.0.0/0
   - Allow Custom TCP: Port 8080 | Source: 0.0.0.0/0
   - Allow HTTP: Port 80 | Source: 0.0.0.0/0

STEP 2: Connect to EC2 via SSH
  ssh -i your-key.pem ubuntu@<EC2-PUBLIC-IP>

STEP 3: Install Docker and Git on EC2
Execute on EC2:
  sudo apt update -y
  sudo apt install -y docker.io git
  sudo systemctl start docker
  sudo systemctl enable docker
  sudo usermod -aG docker ubuntu
  # Apply new group membership:
  newgrp docker

STEP 4: Clone the BookBank GitHub Repository
Execute on EC2:
  cd ~
  git clone https://github.com/savram674/BookBank.git
  cd BookBank

STEP 5: Create a Multi-Stage Dockerfile to Build and Run BookBank
Execute on EC2:
  cat << 'EOF' > Dockerfile
# Stage 1: Build Maven WAR
FROM maven:3.8.4-openjdk-17-slim AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Deploy to Apache Tomcat
FROM tomcat:9.0-jdk17-slim
WORKDIR /usr/local/tomcat/webapps/
RUN rm -rf /usr/local/tomcat/webapps/ROOT
# Copy generated war as ROOT.war for direct root context access
COPY --from=builder /app/target/BookBank.war ./ROOT.war
EXPOSE 8080
CMD ["catalina.sh", "run"]
EOF

STEP 6: Build the Docker Image
Execute on EC2:
  docker build -t bookbank-app:v1 .

STEP 7: Run the Application Container
Execute on EC2:
  docker run -d --name bookbank-container -p 8080:8080 --restart=always bookbank-app:v1

STEP 8: Verify Container and Access Application
Execute on EC2:
  docker ps
  docker logs bookbank-container
  curl http://localhost:8080

STEP 9: Access in Browser
  Open browser: http://<EC2-PUBLIC-IP>:8080/
  (or http://<EC2-PUBLIC-IP>:8080/login.jsp)

WHAT TO SHOW TO MAM:
1. AWS EC2 Console: Show the Running Ubuntu instance details with its Public IPv4 address.
2. Security Groups: Show the Inbound Rule permitting Port 8080 from 0.0.0.0/0.
3. Terminal on EC2: Run `docker ps` showing `bookbank-container` mapped to `0.0.0.0:8080->8080/tcp` with status "Up".
4. Web Browser: Open `http://<EC2-PUBLIC-IP>:8080/` showing the BookBank application (index / login JSP page).

SCENARIO-BASED ANSWERS FOR VIVA / LAB EVALUATION:
Q4.5: Steps to install Maven on Ubuntu and Amazon Linux EC2:
  - On Ubuntu EC2:
    `sudo apt update -y`
    `sudo apt install -y openjdk-17-jdk maven`
    Verify: `mvn -version`
  - On Amazon Linux 2023 EC2:
    `sudo dnf update -y`
    `sudo dnf install -y java-17-amazon-corretto maven`
    Verify: `mvn -version`
Q4.6: Which EC2 feature automates deployment of index.html whenever instance restarts:
  - For Initial Launch: **EC2 User Data (User Data shell script)** under Advanced Details during instance launch automatically executes scripts with root privileges on the first boot.
  - For Every Instance Restart / Reboot:
    1. **EC2 User Data with Cloud-init MIME multi-part script**: Configure cloud-init `runcmd` with `[always]` frequency so it executes on every reboot.
    2. **Crontab `@reboot`**: Add an entry to root's crontab:
       `@reboot /bin/bash /home/ubuntu/deploy.sh`
    3. **Systemd Service Unit**: Create a custom systemd service in `/etc/systemd/system/auto-deploy.service` with `WantedBy=multi-user.target` that executes the deployment script on every system startup.
